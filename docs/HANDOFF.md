## 5. Notes from M4 and M5 worth carrying forward

- Design and decisions: `docs/DECISIONS.md` D10-D18 (accepted 2026-11-17).
- **Small files (for M7):** each MERGE adds 4-8 files (one per shuffle partition), so the few-MB history table ends up with dozens of small files. Good M7 material: compare file counts before and after `OPTIMIZE` (and `ZORDER BY offer_key`, see D15) using `DESCRIBE DETAIL` / `DESCRIBE HISTORY` metrics.
- Real `make run-all` with only the history step new: about 1.5 min for 12 batches (day-1 MERGEs about 5-20 s, change days about 6 s). A full re-run skips everything at about 1 s per batch.
- 3,260 current offers have NULL stock_status: new offers whose qty has never been known (D10).

- **M5 tuning story (good README material):** the first guess (weights 0.45/0.35/0.20, threshold 0.75) gave precision 0.832 and recall 0.807. Wrong pairs were mostly *different products with identical titles and models* (duplicate Amazon listings), which only price separates. A price gate (D30) plus reweighting gave 0.952; best match per vendor (D31) gave 0.989. Scratch tuning scripts are not kept. To re-tune, score candidate pairs, join ground truth on both sides, and grid-search.
- **ER plan shape (`explain()`):** the current-price lookup is a BroadcastHashJoin (Spark auto-broadcast the small table). The blocking self-join is a SortMergeJoin on (brand_key, block_token) with an Exchange (shuffle) on both sides. Biggest dropped blocks are Samsung part-number prefixes (`da97` 795 records, `dc97` 317), split off by hyphens in the titles. **M7 E1** (brand-only vs final blocking) can reuse `candidates.block_pairs` with a different key function.
- **Chained `persist()` blows up plan size (OOM in M5):** a persisted DataFrame still carries its full recipe, and every later query embeds it. ER's 7 chained cached steps made a 1.1 MB plan string that AQE re-printed on each re-plan, so the 1 GB test driver ran out of heap partway through `make test`. The fix is `localCheckpoint()` for chained intermediates (3 KB plans, and real ER went from 87 s to 55 s). Use `persist()` only for single-step reuse. Even after that, the suite still ran out of memory later on, because one shared JVM runs ~120 tests and Spark's default heap is 1 GB. The heap is now `spark.driver_memory: 4g` in `conf/pipeline.yaml` (it only applies when set before the JVM starts). A flood of `ConnectionRefusedError` means the JVM died; find the first real error with `pytest -x`.
- Spark progress bars end with `\r`, so a `print()` can share a line with `[Stage ...]`. Filtering output with `grep -v Stage` hides it; use `tr '\r' '\n'` first.

## 6. Known caveats to carry into the README

- Brand reference table is built from the golden catalogue (optimistic leakage in ER evaluation).
- Ambiguous bare price forms like `1.299` and `1,299`.
- A JSON column that is null in every row might be inferred as string and flagged TYPE_CHANGED (untested).
- A quarantined day cannot be replayed after a later day succeeds for that vendor (accepted limitation from CLAUDE.md).
- Not measured in M7: snapshotPartitions (D9) and OPTIMIZE/ZORDER on offer_history (D15). Bench is one run per variant, so expect a few % noise.
- The 63.8% max price spread (rpt_price_spread) was not investigated; likely an ER false merge.
- SCD2: corrections to an already-loaded day are ignored (D12); absent offers are never closed (D14); a crash retry logs different counts (D18).
- ER: weights are tuned on the same ground truth they are evaluated on (D23, optimistic). A record with no model can chain two different models into one cluster (D25, tested as a known limitation). Brandless records only match via GTIN (D21). The price gate relies on synthetic price behaviour (D30). `master_id` can change between runs (D26).
